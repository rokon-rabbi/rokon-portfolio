> Draft for review. This is a proposed engineering approach, not a report of a pipeline implemented at a particular employer. The examples have not been validated against a live Jenkins installation.

A useful delivery pipeline answers three questions: what was verified, what artifact was produced, and what is allowed to reach an environment. A green build is only meaningful when those answers are repeatable.

Start with a narrow contract. For a hypothetical Maven application, verification means checking out one revision, running the project's build wrapper, collecting test results, and retaining the resulting artifact. Deployment can be added after that contract is dependable.

## Make the build reproducible

Keep the Jenkinsfile beside the application so changes to delivery behavior can be reviewed with code changes. Prefer the checked-in Maven wrapper over whichever Maven binary happens to be installed on an agent. Pin the wrapper distribution and document the JDK requirement. A label such as `linux-java-21` is an agent convention that must actually be configured; it does not install Java.

The following illustrative Declarative Pipeline assumes a Pipeline loaded from source control, an executable Maven wrapper, Java 21 on the selected agent, and the JUnit plugin. It intentionally stops at verification and artifact retention.

```groovy title="Jenkinsfile"
pipeline {
  agent { label 'linux-java-21' }

  options {
    skipDefaultCheckout(true)
    disableConcurrentBuilds()
    timeout(time: 20, unit: 'MINUTES')
    buildDiscarder(logRotator(numToKeepStr: '20'))
  }

  stages {
    stage('Checkout') {
      steps { checkout scm }
    }
    stage('Verify') {
      steps {
        sh './mvnw --batch-mode --no-transfer-progress clean verify'
      }
      post {
        always {
          junit testResults: '**/target/surefire-reports/*.xml',
                allowEmptyResults: false
        }
      }
    }
  }

  post {
    success {
      archiveArtifacts artifacts: '**/target/*.jar', fingerprint: true
    }
  }
}
```

Adapt the report paths for the project. Surefire reports cover unit tests; a project using Failsafe needs its integration-test reports collected too. Multiple modules or multiple JARs also require an explicit rule for selecting the deployable artifact. A fingerprint provides traceability, not proof that an artifact is safe to deploy.

## Treat failures as information

A timeout bounds wasted agent time. It does not fix a hung test or a broken network dependency. Choose a value from expected build duration and then investigate repeated timeouts.

Keep deterministic failures visible. Re-running a failing assertion until it passes can disguise a race condition. A bounded retry may be appropriate for a known transient download failure, provided the operation is safe to repeat and the attempt is logged. Retrying a deployment without understanding its side effects is a different decision.

| Failure | Useful response | Question to answer |
| --- | --- | --- |
| Compilation or assertion failure | Stop verification and retain diagnostics | Is the source change responsible? |
| Missing test reports | Fail the reporting contract | Did tests run, or did the path change? |
| Temporary artifact-service outage | Consider a bounded retry | Can the operation be repeated safely? |
| Deployment health check fails | Stop promotion and inspect the release | What state was actually changed? |

## Separate verification from promotion

Build once, then promote the same identified artifact. Rebuilding separately for each environment can create a mismatch between the tested artifact and the released one.

Before adding deployment, define the environment owner, required approvals, artifact identifier, health checks, and rollback procedure. A manual gate is useful only when the reviewer has enough evidence to make a decision. Document how a release can be stopped and who can restore service.

The example disables overlapping executions of this pipeline. That does not serialize every job that could target the same environment. A shared environment needs coordination across all of its writers.

## Keep credentials within the boundary

Use Jenkins credential bindings rather than putting secrets into the repository or command text. Scope credentials to the job's purpose and keep untrusted pull-request execution away from release credentials. Console masking is helpful, but a script with access to a secret can still misuse it.

Review shell tracing, command arguments, archived files, and workspace contents before introducing a credential. The intended result is a short-lived, narrowly scoped operation—not a broadly privileged build agent.

## Verify the pipeline before relying on it

Exercise the failure paths in a non-production job: a failing test, an empty report directory, an agent outage, an interrupted build, and two overlapping runs. Check that status, logs, and retained artifacts explain each result. Add a deployment stage only after the promotion and recovery contracts can be demonstrated safely.

There are no performance figures or reliability claims attached to this example. A real case study would need its own environment details, measured evidence, and permission to share them.
